How the Linux Command Vault is built

The vault is the field guide I keep for Linux administration: a cheat sheet for every command I use, playbooks for when things break, and longer guides. I write it in Obsidian, a generator does the repetitive parts, and every push publishes it to linux.marcuswalton.dev.

Why build it this way

Most of what a sysadmin needs at 3am is the right command with the right flags, and the order to check things in. I wanted that in one place I could search offline, link together and keep up to date, rather than spread over bookmarks and shell history. Obsidian gives me plain Markdown files in a Git repository, so the vault has no lock-in and every change has a history.

Writing hundreds of cheat sheets by hand, and keeping their indexes in step, would be slow and easy to get wrong. So the structured parts are generated and the parts that need judgement are written by hand.

Generated where it's repetitive, hand-written where it matters

  • Command notes come from data. Each command is an entry in a Python data file: syntax, key options, real examples, gotchas and related commands. A generator turns those into notes with a consistent layout, links each one to its man page, and rebuilds the category maps and the counts on the home page.
  • Playbooks start from the symptom. Each one begins with what you actually see (a full disk, a service that won't start, a certificate that expired), lists the likely causes, and gives the commands to confirm and fix each one. They follow a shared template so they read the same way under pressure.
  • Guides go deeper. Kernel tuning, Proxmox and KVM, WireGuard, Kubernetes, Ceph, database replication and failover, mail servers, security hardening, and scripting in Bash, Python, C, Go and Rust.
  • The generator never overwrites hand-written notes. It only owns the files it creates and a few marked sections, so regenerating is always safe.

Publishing without leaking anything

The vault also holds notes that are only for me, such as records of my own systems, and the man pages, which belong to other projects under their own licences. The website must never include them, even by accident.

  • An allowlist, not a blocklist. The build copies only the folders it's told to publish. A new folder stays private until I add it to the list, so forgetting something fails safe.
  • Links are rewritten on the way out. Links to man page notes become links to the online man page, and links to anything unpublished become plain text, so the site has no dead links and gives no hints about what's held back.
  • Private records never reach Git. The folders for my own systems are ignored by Git, so only their empty structure is in the repository.

The build

Every push to the repository triggers a Cloudflare Workers build, and the site is live about two minutes later. The build uses Quartz pinned to an exact release and commit, so an upstream change can't alter the site without me noticing. The graph view's libraries are downloaded once at pinned versions, checked against SHA-256 checksums and served from the site itself rather than a CDN. The build also hashes every inline script, so the Content-Security-Policy can allow exactly those scripts and nothing else.

A small Cloudflare Worker serves the result with the same security headers as this site. The build also writes the vault's note counts to a small JSON file, which this site's Worker reads to keep the numbers on the homepage up to date.

Testing the examples

A cheat sheet with a wrong flag is worse than none, so most examples are run in a throwaway lab before they go in: Podman containers for services, and QEMU virtual machines where a container can't do the job. A few examples:

  • Kubernetes and Helm against k3s running inside rootless Podman, which needed its own set of kubelet and cgroup workarounds that went into the notes as well.
  • Proxmox VE installed unattended from an answer file into a nested two-node cluster, to test the clustering and HA commands.
  • OPNsense booted in QEMU and driven over its serial console by a short Python script.
  • Mail: two Postfix and Dovecot servers with rspamd, plus a local DNS server holding the MX, SPF, DKIM, DMARC and reverse records, to test delivery and authentication end to end.

The surprises are often the most useful part. Debian loads its ModSecurity settings before the Core Rule Set, so rule exclusions only work in specific files. rspamd caches SPF and DKIM results, so it has to be restarted after a DNS change. Lessons like these end up in the notes as gotchas.

Where something couldn't be tested, the note says so. Real hardware faults can't be reproduced in a container, for example, so the hardware notes are checked for command syntax and output only. Labs are torn down when the work is done.

What I took from it

Documentation stays useful when it's cheap to keep up to date. Generating the structured parts, testing the examples and automating the publishing mean that adding a note is the only manual step. The private-by-default publishing step was worth getting right early: it's what lets me keep everything in one vault.
