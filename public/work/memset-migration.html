Migrating ~1,100 virtual servers onto OnApp

When iomart brought Memset into the group, Memset's VPS customers were still running on Memset's own in-house hosting platform. I led a team of three to move that estate onto OnApp, and carried out over half of the migrations myself, so it could be run alongside the rest of iomart's infrastructure.

From

The problem

Running a separate, home-grown hosting platform for one part of the business meant separate tooling, separate processes and separate knowledge to keep it alive. Moving it onto OnApp, a standard cloud management platform, put those servers on the same footing as the rest of the estate and made them easier to support long term.

The hard part was that these were live customer servers. Every one of them belonged to someone who expected it to keep working, and the migration had to happen without turning into 1,100 support tickets.

The approach

  • Inventory first. Catalogued the existing estate: which servers existed, what they ran, which customers owned them, and which ones needed special handling.
  • Prove the process on a small batch. Migrated a first group to shake out problems with the procedure before scaling it up.
  • Move in planned batches. Worked through the estate at 50–60 servers a day over six months, rather than all at once, so any issue stayed small and contained.
  • Keep customers informed. Customers were told what was happening and when, so a migration window never came as a surprise.
  • Validate on the other side. Checked each server after the move (booting, networking, services and data) before treating it as done.

How each server moved

Each migration was started by hand and carried out by a script, so every server went through the same steps:

  1. Prepare the source. The script first brought the server's features up to date, so it would run correctly on the new platform.
  2. Create the new VM. It built a matching virtual machine on OnApp to receive the data.
  3. Hot copy. With the original server still running, rsync copied its data across, so the customer stayed online for the bulk of the transfer.
  4. Cold sync. The original server was then shut down and a final rsync copied anything that had changed, so nothing written during the hot copy was lost.
  5. Verify and cut over. Once the new server was confirmed to boot, its IP address and firewall rules were moved across from the old one.

Because the bulk of the data moved while the server was still live, each customer was only offline for the final sync and the IP move: 10–20 minutes on average.

When a move failed

The script assumed a server used the default configuration, and most did. Around 2–3 a week did not, and their migrations failed. Because the original server was left untouched until the cutover, each of those was rolled back by bringing the original back up, so the customer was returned to a working server rather than left with a broken one. The server was then fixed and migrated again at a later date.

Why it was built this way

  • Downtime depended on change, not size. rsync only sends what differs, so the cold sync copied just the files that changed during the hot copy. A large server with little activity was offline for about as long as a small one.
  • The old server stayed intact until the end. Copying only reads from the original, and nothing moved away from it until the new VM had booted. That is what made the 2–3 failed moves a week simple to roll back.
  • Customers kept their address. Moving the IP rather than assigning a new one meant customers had nothing to update. Where DNS changes were needed for domains hosted with us, our team made them. Moving the firewall rules with it kept their access rules exactly as they were.
  • One script, every server. Running the same steps every time made the 1,000th migration as predictable as the first, and made a failure easy to spot because it broke a known pattern.

The result

Around 1,100 customer virtual servers were moved off the legacy platform and onto OnApp in six months, each offline for 10–20 minutes on average. That brought Memset's VPS customers into iomart's systems and left one fewer bespoke platform to maintain. Customers kept their IP addresses and firewall rules, so for most of them the move came down to a short planned outage and nothing to reconfigure.

What I took from it

Large migrations are mostly planning, communication and checking, with the actual data movement being the easy part. A repeatable, tested procedure is what makes the thousandth server as uneventful as the tenth.

Splitting the copy into a live pass and a short final pass is the single choice that did most for customers: it kept each outage to the final sync rather than the whole transfer, 10–20 minutes instead of hours. Keeping the original untouched until the cutover meant every move had a way back, which made it safe to keep up a steady pace day after day.
